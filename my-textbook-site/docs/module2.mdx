# Module 2: The Digital Twin (Gazebo & Unity)

In this module, we bridge the gap between pure code and the physical world. A **Digital Twin** is more than just a 3D model; it's a physics-based, dynamic, virtual replica of a humanoid robot. It's our sandbox, our testing ground, and our most powerful tool for developing and verifying complex behaviors safely and efficiently. We will explore two key platforms: **Gazebo** for robust physics simulation and **Unity** for high-fidelity visualization and interaction.

## Section 1: Foundations of Robotics Simulation

*(Based on Tasks T1.1, T1.2, T1.3, T1.4)*

### The Digital Twin Concept

A digital twin is a living model that mirrors a physical object. For humanoid robotics, this means creating a virtual robot that is functionally identical to the real one. It has the same mass, joint constraints, and sensor properties. When the real robot's software commands it to move its arm, the digital twin's arm moves in the exact same way.

**Key Benefits**:
-   **Safety**: Testing a new walking algorithm is risky. A fall can cost thousands of dollars in repairs. In simulation, a fall costs nothing.
-   **Speed**: You can run simulations faster than real-time to quickly gather data or test long-duration tasks.
-   **Parallelization**: You can run hundreds of simulations at once on a server to test many different scenarios or train an AI model.
-   **Reproducibility**: Isolating a bug is easier when you can perfectly replicate the conditions that caused it.

### The Simulation Ecosystem: Gazebo vs. Unity

No single tool does everything perfectly. We use a combination of two industry-leading platforms:

-   **Gazebo**: The Physics Lab. Gazebo is an open-source simulator that excels at robotics-centric physics. It accurately models gravity, friction, contact forces, and motor torques. Its primary job is to compute the "ground truth" of the simulation. It's powerful, but not known for photorealistic graphics.

-   **Unity**: The Film Set. Unity is a professional game engine renowned for its stunning graphics, intuitive editor, and rich tools for creating interactive experiences. We use Unity to visualize the simulation in high fidelity and to build human-robot interaction (HRI) scenarios.

Think of it this way: **Gazebo runs the numbers, Unity makes it look good and feel interactive.** They communicate via ROS 2.

### Understanding SDF: The Language of Simulation

While URDF (from Module 1) is great for describing a robot's kinematics, it lacks tags for describing the environment. The **Simulation Description Format (SDF)** is a superset of URDF that allows you to define everything in a simulation, including:
-   Robots (often by including a URDF)
-   Lighting
-   Physics parameters
-   Environments (terrain, buildings)
-   Sensor properties and plugins

You'll use SDF to create Gazebo worlds and to add simulation-specific details to your robot model.

### Installation and Setup

For this module, you will need to install Gazebo and the necessary ROS 2 integration packages.
1.  **Install Gazebo**: Follow the official installation guide. We'll be using Gazebo Garden.
2.  **Install ROS 2-Gazebo Bridge**: This package provides the nodes and messages needed to communicate between ROS 2 and Gazebo.

## Section 2: Physics-Based Simulation with Gazebo

*(Based on Tasks T2.1, T2.2, T2.3, T2.4, T2.5)*

### Creating a Gazebo World

A Gazebo "world" is an SDF file that defines an environment. Let's create a simple world with a ground plane and basic lighting.

```xml
<!-- simple_world.sdf -->
<?xml version="1.0" ?>
<sdf version="1.7">
  <world name="default">
    <plugin
      name="gz::sim::systems::Physics"
      filename="gz-sim-physics-system"/>
    <plugin
      name="gz::sim::systems::UserCommands"
      filename="gz-sim-user-commands-system"/>
    <plugin
      name="gz::sim::systems::SceneBroadcaster"
      filename="gz-sim-scene-broadcaster-system"/>

    <light type="directional" name="sun">
      <cast_shadows>true</cast_shadows>
      <pose>0 0 10 0 0 0</pose>
    </light>

    <model name="ground_plane">
      <static>true</static>
      <link name="link">
        <collision name="collision">
          <geometry>
            <plane>
              <normal>0 0 1</normal>
            </plane>
          </geometry>
        </collision>
        <visual name="visual">
          <geometry>
            <plane>
              <normal>0 0 1</normal>
              <size>100 100</size>
            </plane>
          </geometry>
          <material>
            <ambient>0.8 0.8 0.8 1</ambient>
            <diffuse>0.8 0.8 0.8 1</diffuse>
            <specular>0.8 0.8 0.8 1</specular>
          </material>
        </visual>
      </link>
    </model>
  </world>
</sdf>
```
To run this world, save it as `simple_world.sdf` and run:
```bash
gz sim simple_world.sdf
```

### Spawning a Humanoid

To add your humanoid robot (described in a URDF file, e.g., `humanoid.urdf`) to the simulation, you use a Gazebo plugin that spawns entities. You can do this from the command line or, more commonly, from a ROS 2 launch file.

```bash
# Example command to spawn a robot
gz service -s /world/default/create --reqtype gz.msgs.EntityFactory \
--reptype gz.msgs.Boolean -p 'sdf_filename: "path/to/your/humanoid.urdf", name: "my_humanoid"'
```

### Configuring Physics and Collisions

Realism comes from tuning the physics. In your SDF/URDF, you can define `<collision>` and `<inertial>` tags for each link. For joints, you can define friction and damping.

```xml
<link name="left_foot">
  <inertial>
    <mass>1.2</mass>
    <inertia>
      <ixx>0.1</ixx> <ixy>0</ixy> <ixz>0</ixz>
      <iyy>0.1</iyy> <iyz>0</iyz>
      <izz>0.1</izz>
    </inertia>
  </inertial>
  <collision name="foot_collision">
    <geometry>
      <box size="0.3 0.15 0.05" />
    </geometry>
    <surface>
      <contact>
        <collide_bitmask>0x01</collide_bitmask>
      </contact>
      <friction>
        <ode>
          <mu>0.8</mu>  <!-- Static friction coefficient -->
          <mu2>0.8</mu2> <!-- Dynamic friction coefficient -->
        </ode>
      </friction>
    </surface>
  </collision>
  ...
</link>
```

### ROS 2 Integration: The `ros_gz_bridge`

The bridge is the key to communication. It relays messages between ROS 2 topics and Gazebo Transport topics.

To bridge the simulated joint states to a ROS 2 topic, you would run:
```bash
ros2 run ros_gz_bridge parameter_bridge /joint_states@sensor_msgs/msg/JointState@gz.msgs.Model
```
Now, you can use `ros2 topic echo /joint_states` to see the same data your real robot would produce.

## Section 3: Simulating the Senses

*(Based on Tasks T3.1, T3.2, T3.3, T3.4, T3.5)*

Sensors are added to your robot model using the `<sensor>` tag in your SDF/URDF file, powered by Gazebo's sensor plugins.

### Simulating an RGB Camera

This snippet, added to a link (e.g., the head), creates a simulated camera.

```xml
<sensor name="rgb_camera" type="camera">
  <camera>
    <horizontal_fov>1.047</horizontal_fov>
    <image>
      <width>1920</width>
      <height>1080</height>
    </image>
  </camera>
  <always_on>1</always_on>
  <update_rate>30</update_rate>
  <plugin
    name="camera_publisher"
    filename="libgz-sim-camera-system.so">
    <topic>/camera</topic>
  </plugin>
</sensor>
```
The plugin publishes image data on the Gazebo topic `/camera`. You can then bridge this to a ROS 2 topic.

### Simulating a Depth Camera (and LiDAR)

A depth camera works similarly but uses `type="depth_camera"`. A LiDAR uses `type="gpu_lidar"`. Each has specific parameters to control its field of view, range, and resolution.

```xml
<sensor name="lidar" type="gpu_lidar">
  <scan>
    <horizontal>
      <samples>360</samples>
      <resolution>1</resolution>
      <min_angle>-3.14</min_angle>
      <max_angle>3.14</max_angle>
    </horizontal>
  </scan>
  <range>
    <min>0.1</min>
    <max>10.0</max>
  </range>
  ...
</sensor>
```

### Adding Realistic Noise

To better mimic the real world, you can add noise models to your sensor data.

```xml
<sensor name="imu_sensor" type="imu">
  <imu>
    <angular_velocity>
      <x>
        <noise type="gaussian">
          <mean>0.0</mean>
          <stddev>0.01</stddev>
        </noise>
      </x>
      ...
    </angular_velocity>
  </imu>
  ...
</sensor>
```
This adds Gaussian noise to the IMU's angular velocity readings, making your simulation more robust.

## Section 4: High-Fidelity Visualization with Unity

*(Based on Tasks T4.1, T4.2, T4.3, T4.4)*

While Gazebo handles physics, we use Unity for photorealistic rendering and interaction.

### Setting up Unity with ROS 2

1.  Create a new Unity project.
2.  Install the [Unity Robotics Hub](https://github.com/Unity-Technologies/Unity-Robotics-Hub) packages, specifically the `ROS-TCP-Connector`.
3.  Configure the TCP Connector to connect to the IP address of your ROS 2 machine.

### Visualizing the Robot

The process involves two main steps:
1.  **Exporting the Robot Model**: Export your humanoid's visual meshes (as `.fbx` or `.obj` files).
2.  **Writing a Unity Script**: Create a C# script that subscribes to the `/joint_states` ROS 2 topic (via the TCP Connector). In the script's `Update()` loop, apply the received joint angles to the corresponding `Transform` components of the robot model in Unity.

### Creating an Interactive UI

Unity's UI system makes it easy to create interfaces. You can create a button that, when clicked, publishes a message to a ROS 2 topic. This allows a user in the Unity simulation to trigger a behavior (like waving or walking) that is executed by your ROS 2 control nodes.

## Section 5: Bridging the Reality Gap (Sim-to-Real)

*(Based on Tasks T5.1, T5.2, T5.3, T5.4)*

A simulation is only useful if it predicts reality. The "reality gap" is the difference between simulated and real-world behavior.

-   **System Identification**: If your real robot consistently overshoots a target, it means your simulated motor parameters (like damping) are wrong. System identification is the process of running tests on the real robot to measure its physical properties, which you then plug back into your SDF.

-   **Domain Randomization**: Instead of trying to create one perfect simulation, create thousands of slightly different ones. In each simulation, randomly vary parameters like:
    -   Lighting conditions
    -   Friction coefficients
    -   Sensor noise levels
    -   Mass and center of gravity of links
    
    If you train an AI controller on this varied data, it learns to be robust to these variations and is much more likely to work on the real robot without modification. This is a cornerstone of modern robotics AI.
