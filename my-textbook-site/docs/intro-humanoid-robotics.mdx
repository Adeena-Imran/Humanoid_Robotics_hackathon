# Module 1: The Robotic Nervous System (ROS 2)

Welcome to the foundational module of our journey into humanoid robotics. Before we can make a robot walk, talk, or think, we must first build its nervous system. In modern robotics, that nervous system is the Robot Operating System (ROS). This module focuses on ROS 2, the next-generation middleware that provides the communication backbone for nearly all advanced robotic systems, including humanoids.

## Section 1: Introduction to ROS 2 - The "What" and "Why"

*(Based on Tasks T1.1, T1.2, T1.3, T1.4)*

### What is a Robotics Middleware?

Imagine building a humanoid robot. You have dozens of motors (actuators), cameras and gyroscopes (sensors), and multiple computers for processing AI, motion planning, and decision-making. How do all these components, often running on different parts of the robot and written in different programming languages, communicate with each other reliably and in real-time?

This is the problem that a **robotics middleware** solves. It's a software layer that sits between the operating system and the robot's application code, providing standardized services like:
-   **Message Passing**: Allowing different processes to exchange data.
-   **Hardware Abstraction**: Providing a common interface to control different types of hardware.
-   **Tooling**: Offering utilities for visualization, debugging, and simulation.

For a complex system like a humanoid robot, a middleware isn't just helpful—it's essential. It provides the structure that turns a collection of disparate parts into a single, coherent system.

### A Brief History: From ROS 1 to ROS 2

The original Robot Operating System (ROS 1) was a game-changer, providing a common platform for robotics research and development. However, as robotics moved from the lab into the real world, its limitations became clear. ROS 1 was not designed for multi-robot systems, real-time control, or use in commercial, mission-critical products.

Enter **ROS 2**. It was redesigned from the ground up to meet these challenges, built on top of the industrial-grade **DDS (Data Distribution Service)** standard. The key advantages of ROS 2 include:
-   **Real-Time Support**: Enables more precise and deterministic control over robot hardware.
-   **Enhanced Reliability**: Offers configurable quality of service (QoS) settings for message delivery.
-   **Multi-Robot and Network Support**: Designed for distributed systems, allowing multiple robots to communicate easily.
-   **Commercial-Grade**: Supported by a global community and suitable for production environments.

### Your First ROS 2 Steps: Installation and Verification

We assume you are using a Linux environment, as it is the primary platform for ROS development. The official ROS 2 documentation provides the most up-to-date installation instructions.

1.  **Install ROS 2**: Follow the official guide for your Linux distribution (we recommend Ubuntu 22.04 with ROS 2 Humble).
    -   [ROS 2 Humble Installation Guide](https://docs.ros.org/en/humble/Installation.html)

2.  **Verify the Installation**: Once installed, source your ROS 2 setup file and test the installation by running the built-in `talker` and `listener` demo nodes. Open two separate terminal windows.

    In the first terminal, run the `talker`:
    ```bash
    source /opt/ros/humble/setup.bash
    ros2 run demo_nodes_cpp talker
    ```

    In the second terminal, run the `listener`:
    ```bash
    source /opt/ros/humble/setup.bash
    ros2 run demo_nodes_cpp listener
    ```
    You should see the `talker` publishing "Hello World" messages and the `listener` receiving them. This confirms that your ROS 2 communication layer is working correctly.

### Essential ROS 2 Command-Line Tools

ROS 2 comes with a powerful set of command-line tools for inspecting and interacting with your robotic system.

| Command             | Description                                                                  |
|---------------------|------------------------------------------------------------------------------|
| `ros2 run <pkg> <exec>` | Executes a specific node from a package.                                     |
| `ros2 node list`      | Lists all currently running nodes in the ROS graph.                          |
| `ros2 topic list`     | Lists all active topics.                                                     |
| `ros2 topic echo <topic_name>` | Prints the data currently being published on a topic.               |
| `ros2 service list`   | Lists all available services.                                                |
| `ros2 service call <srv_name> <srv_type> <args>` | Calls a service with the specified arguments.      |
| `ros2 action list`    | Lists all available actions.                                                 |
| `ros2 bag record <topics...>` | Records messages on specified topics to a file (a "rosbag").         |

## Section 2: Core ROS 2 Communication Concepts

*(Based on Tasks T2.1, T2.2, T2.3, T2.4, T2.5, T2.6)*

At the heart of ROS 2 is a graph of processes (nodes) that communicate with each other. This section details the primary communication patterns you will use.

### Nodes: The Building Blocks

A **Node** is the fundamental processing unit in ROS 2. Think of it as a single, executable program responsible for one specific task. For a humanoid robot, you might have separate nodes for:
-   Reading data from the IMU (Inertial Measurement Unit).
-   Controlling the motors in the left leg.
-   Running a face detection algorithm on a camera feed.
-   Planning the robot's footsteps.

Each node is an independent entity that can be started, stopped, and restarted without affecting the others, making the system modular and fault-tolerant.

### Topics: For Continuous Data Streams

**Topics** are the most common communication method. They operate on a **publish-subscribe** pattern, perfect for continuous data streams where one node produces data and multiple nodes might need to consume it.

-   **Publisher**: A node that pushes messages onto a topic.
-   **Subscriber**: A node that receives messages from a topic.

*Example*: A humanoid's camera node would **publish** image frames to an `/image_raw` topic. A face detection node and a navigation node could both **subscribe** to this same topic to receive the images for their respective tasks.

![Topic Communication](https://docs.ros.org/en/humble/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Images/topics.png)

### Services: For Request/Reply Interactions

**Services** are used for synchronous, two-way communication. A client node sends a request to a service server and waits for a response. This is ideal for tasks that are transactional in nature.

*Example*: A control node might call a `/get_joint_angle` service on a motor controller node. The control node sends the name of the joint it's interested in and blocks (waits) until the motor controller responds with the current angle.

![Service Communication](https://docs.ros.org/en/humble/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Services/Images/services.png)

### Actions: For Long-Running, Feedback-Driven Tasks

**Actions** are for long-running, asynchronous tasks that require feedback and the ability to be preempted or cancelled. An action consists of three parts: a goal, feedback, and a result.

*Example*: Commanding a humanoid to "walk to the kitchen" is a perfect use case for an action.
-   **Goal**: The target destination (kitchen coordinates).
-   **Feedback**: The robot's current position and distance from the goal, sent periodically.
-   **Result**: A confirmation that the robot has arrived or a failure message if it got stuck.
The main control node can send the goal and then continue with other tasks while monitoring the feedback. It can also send a cancellation request at any time.

### Topics vs. Services vs. Actions

| Communication Type | Use Case                                  | Pattern              | Synchronicity |
|--------------------|-------------------------------------------|----------------------|---------------|
| **Topic**          | Continuous data streams (e.g., sensor data) | Publish-Subscribe    | Asynchronous  |
| **Service**        | Quick, transactional tasks (e.g., query)  | Request/Reply        | Synchronous   |
| **Action**         | Long-running, feedback-driven tasks (e.g., navigation) | Goal/Feedback/Result | Asynchronous  |

### A Note on QoS (Quality of Service)

Because ROS 2 is built on DDS, you can fine-tune the "Quality of Service" for each topic, service, or action. The two most important settings are:
-   **Reliability**: `Best Effort` (fast but may drop messages) or `Reliable` (guarantees delivery). Use `Best Effort` for high-frequency data like video feeds where a dropped frame is okay, and `Reliable` for critical commands.
-   **Durability**: `Volatile` (subscribers only get messages sent after they subscribe) or `Transient Local` (new subscribers get the last message that was sent, even if they subscribe later). `Transient Local` is great for topics that publish state data, like a robot's configuration.

## Section 3: Practical ROS 2 with `rclpy`

*(Based on Tasks T3.1, T3.2, T3.3, T3.4, T3.5, T3.6, T3.7)*

Let's move from theory to practice using `rclpy`, the official Python client library for ROS 2.

### Creating a ROS 2 Workspace and Package

A **workspace** is a directory where you build and manage your ROS 2 packages. A **package** is a container for your nodes, launch files, and other resources.

```bash
# Create a workspace directory
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/

# Create a new package
ros2 pkg create --build-type ament_python my_first_package --dependencies rclpy sensor_msgs
```

### Writing a Publisher Node (`rclpy`)

This node will publish mock `JointState` messages, simulating a humanoid's joint positions.

Create a file named `joint_publisher.py` inside `my_first_package/my_first_package/`:
```python
# my_first_package/my_first_package/joint_publisher.py
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import Header

class JointStatePublisher(Node):
    def __init__(self):
        super().__init__('joint_state_publisher')
        self.publisher_ = self.create_publisher(JointState, 'joint_states', 10)
        self.timer = self.create_timer(0.5, self.timer_callback)
        self.get_logger().info('Joint State Publisher has been started.')

    def timer_callback(self):
        msg = JointState()
        msg.header = Header()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.name = ['left_hip_joint', 'left_knee_joint', 'right_hip_joint', 'right_knee_joint']
        msg.position = [0.1, -0.5, -0.1, 0.5] # Mock positions in radians
        msg.velocity = []
        msg.effort = []
        self.publisher_.publish(msg)
        self.get_logger().info(f'Publishing: "{msg.position}"')

def main(args=None):
    rclpy.init(args=args)
    joint_state_publisher = JointStatePublisher()
    rclpy.spin(joint_state_publisher)
    joint_state_publisher.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```
*This publisher creates a `JointState` message every 0.5 seconds and publishes it to the `/joint_states` topic.*

### Writing a Subscriber Node (`rclpy`)

This node will listen to the `/joint_states` topic and print the received data.

Create `joint_subscriber.py` in the same directory:
```python
# my_first_package/my_first_package/joint_subscriber.py
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState

class JointStateSubscriber(Node):
    def __init__(self):
        super().__init__('joint_state_subscriber')
        self.subscription = self.create_subscription(
            JointState,
            'joint_states',
            self.listener_callback,
            10)
        self.get_logger().info('Joint State Subscriber has been started.')

    def listener_callback(self, msg):
        self.get_logger().info(f'I heard: "Positions: {msg.position}"')

def main(args=None):
    rclpy.init(args=args)
    joint_state_subscriber = JointStateSubscriber()
    rclpy.spin(joint_state_subscriber)
    joint_state_subscriber.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

## Section 4: Describing Robots with URDF

*(Based on Tasks T4.1, T4.2, T4.3, T4.4, T4.5)*

### Introduction to URDF

The **Unified Robot Description Format (URDF)** is an XML format used to describe the physical model of a robot. It defines the robot's **links** (physical parts), **joints** (how links connect), and visual properties. URDF is essential for simulation, visualization (in tools like RViz2), and motion planning.

### A Simple Two-Link Arm URDF

Let's create a URDF for a simple arm with two links and one joint.

```xml
<!-- simple_arm.urdf -->
<robot name="simple_arm">
  <!-- Base Link -->
  <link name="base_link">
    <visual>
      <geometry>
        <cylinder length="0.6" radius="0.2"/>
      </geometry>
    </visual>
  </link>

  <!-- Arm Link -->
  <link name="arm_link">
    <visual>
      <geometry>
        <box size="0.8 0.2 0.2"/>
      </geometry>
      <origin xyz="0.4 0 0" rpy="0 0 0"/>
    </visual>
  </link>

  <!-- Joint connecting base to arm -->
  <joint name="base_to_arm_joint" type="revolute">
    <parent link="base_link"/>
    <child link="arm_link"/>
    <origin xyz="0 0 0.3" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-3.14" upper="3.14" effort="10" velocity="1.0"/>
  </joint>
</robot>
```

### URDF Joint Types

| Joint Type   | Motion                                        | Humanoid Example                |
|--------------|-----------------------------------------------|---------------------------------|
| `revolute`   | Rotates around a single axis (like an elbow). | Knee, elbow, hip rotation       |
| `continuous` | A revolute joint with no angle limits.        | A spinning sensor, wheel        |
| `prismatic`  | Slides along a single axis (linear motion).   | A linear actuator in the torso  |
| `fixed`      | A rigid connection with no motion.            | Connecting a camera to the head |

### Visualizing URDF in RViz2

To see your robot model, you need to publish its state to ROS. You can use the `robot_state_publisher` and `joint_state_publisher` tools to do this, and then visualize it in RViz2. This process brings your XML description to life as a 3D model.

### Simplified Humanoid URDF

A full humanoid URDF is very complex, but it's built from the same simple `link` and `joint` elements. Here is a conceptual snippet showing how a torso, head, and arm might be connected.

```xml
<robot name="simple_humanoid">
  <!-- Torso is the base -->
  <link name="torso_link">...</link>

  <!-- Head connected to torso -->
  <joint name="neck_joint" type="revolute">
    <parent link="torso_link"/>
    <child link="head_link"/>
    ...
  </joint>
  <link name="head_link">...</link>

  <!-- Arm connected to torso -->
  <joint name="shoulder_joint" type="revolute">
    <parent link="torso_link"/>
    <child link="upper_arm_link"/>
    ...
  </joint>
  <link name="upper_arm_link">...</link>
</robot>
```
*This hierarchical structure of parent-child links forms the kinematic chain of the robot.*

### Glossary
- **Node**: A ROS 2 process performing a single task.
- **Topic**: A communication channel for continuous data streams.
- **Service**: A request/reply communication method.
- **Action**: A communication method for long-running, feedback-driven goals.
- **rclpy**: The Python client library for ROS 2.
- **URDF**: XML format for describing a robot's physical structure.
- **QoS**: Quality of Service, settings for tuning communication reliability and durability.
